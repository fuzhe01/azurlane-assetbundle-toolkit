## 二、R3：命中判定修复（核心缺陷）

### 问题

点鞋/丝袜/衣角的热区，实际触发的却是**戒指**。

### 根因

`gallery_src/index.html` 的 `costumeHitAt()` 实现「落进盒子的候选里取 `area` 最小者」（最具体优先，**规则本身正确**）。

但只驱动 1 个 drawable 的参数包围盒极小：

```
Paramring   w=0.293  h=0.175  area=0.051   ← 1 个 drawable
Cloth1      w=1.548  h=1.086  area=1.681   ← 4 个 drawable
```

`Paramring` 比第二名小 **33 倍**，于是**任何**落在大盒子里的点都被它以「面积最小」抢走。

旧阈值 `1e-3` 只挡「严格退化成一点」，挡不住这种「小到必胜」的盒子。

### 修法

`gallery_src/index.html` 的 `costumeBoxes()`，**过小包围盒向外扩张到最小可点击尺寸**（中心不变），而不是丢弃：

```js
const COS_MIN_SIDE=0.5;
if(w<COS_MIN_SIDE){ const c=(x0+x1)/2; x0=c-COS_MIN_SIDE/2; x1=c+COS_MIN_SIDE/2; w=COS_MIN_SIDE; }
if(h<COS_MIN_SIDE){ const c=(y0+y1)/2; y0=c-COS_MIN_SIDE/2; y1=c+COS_MIN_SIDE/2; h=COS_MIN_SIDE; }
```

**为什么扩张而非丢弃**：丢弃会让戒指/项圈彻底点不到，等于砍功能。扩张后它仍是最小者、优先级最高，但只在**自己周围**获胜，不再劫持远处的大热区。

**阈值 0.5 的依据**：实测其余 7 个参数的 `min(w,h)` 全部 ≥1.05（Cloth1 最小 1.086），0.5 约为其一半。

### 验证（`diag_hit_distribution.py`）

在**每个参数自己的包围盒区域内逐点扫描**（步长 4px），统计每个点命中的是谁：

| 参数 | 采样点 | 命中分布 | 最佳真实命中点 |
|---|---|---|---|
| Stock1 | 2254 | Stock1=2254 | (684,442) → Stock1 ✅ |
| Stock2 | 7040 | Stock2=4122, Stock1=2303, ShoseOff=525, Cloth1=90 | (594,484) → Stock2 ✅ |
| Paramring | 8 | Paramring=8 | (922,393) → Paramring ✅ |
| Cloth1 | 130 | Cloth1=130 | (814,490) → Cloth1 ✅ |
| Cloth2 | 1357 | Cloth2=1347, Paramring=10 | (966,474) → Cloth2 ✅ |
| Cloth3 | 169 | Cloth3=169 | (868,409) → Cloth3 ✅ |
| ShoseOff | 500 | ShoseOff=500 | (513,412) → ShoseOff ✅ |

## 三、R4：参数写入是否到达渲染

### 遗留矛盾

`probe_costume_write_timing.py` 的 docstring 记着：

> 热区点击后参数确实变成 1 且稳定，但「pins 稳态 lo=-1 vs hi=1」逐 drawable 比对为 **0 差异**；而同一 evaluate 内强制 `im.update()` 再比，却有 2 个 drawable 差异。

### 结论：写入**确实到达渲染**，旧矛盾是判据用错

`verify_r4_param_to_render.py` 用**顶点包围盒**（不是不透明度）做判据：

```
ShoseOff: 0 → 1
drawable 460:  w 2.4017 → 2.4449   x0 -9.9973 → -10.2100   y0 -1.2680 → -1.3589
drawable 461:  w 2.3175 → 2.3722   x0 -9.9535 → -10.1576   y0 -1.2679 → -1.3583
变化集合与 param_drawables 的交集: [460, 461]  ✓
```

**旧矛盾的解释**：当时比对的是 **opacity**，而 `ShoseOff` 改变的是**顶点位置**——鞋子是「挪了位置」而不是「隐身」，不透明度全程为 1，所以看起来「0 差异」。

## 四、R6：真实点击验收

### 为什么必须这一层

直接调 `__costumeToggle` 只证明「函数能跑」，不证明「用户点得到」。`onUp` 里的接续顺序（`stateFind` → `costumeHitAt` → 播动作）写反了，前三层全绿而真实点击无效。

### 做法

用 CDP `Input.dispatchMouseEvent` 派发真实 `mouseMoved` + `mousePressed` + `mouseReleased`，**不调用任何内部函数**。

### 结果：四种参数类型全 PASS

| 参数 | 类型 | 点击点 | 参数变化 | 组名 | pill |
|---|---|---|---|---|---|
| `ShoseOff` | slider(-1..1) | (513,411) | 0→1 | idle→idle | 「鞋 · ShoseOff → 1」 |
| `Stock1` | switch | (692,438) | 0→1 | idle→idle | 「丝袜 · Stock1 → 1」 |
| `Cloth2` | switch（12部件） | (995,474) | 0→1 | idle→idle | 「衣服 · Cloth2 → 1」 |
| `NeckMoney` | switch（单部件） | (844,433) | 0→1 | idle→idle | 「项圈 · NeckMoney → 1」 |

**组名全部保持 `idle`**，说明没有误触动作分支。

## 五、平行会话的改动（不是我做的，但影响本次验收环境）

另一个 copilot 会话在同一时段修了**回落双路径竞争**，已写进 `PROJECT_STATUS.md`：

### 它发现的问题

旧版有**两条**回落路径，互相踩踏：

| 路径 | 选组方式 | 优先级 | pose_keep |
|---|---|---|---|
| A `_fallback()` | 库 `startRandomMotion` + 1200ms 看门狗，只放行 `touch_%`，其它固定回 idle | NORMAL(2) | 不写 |
| B `_fallbackToIdle()` | `setTimeout(duration+0.6s)`，读 chain 表选组 | IDLE(1) | 写 |

A 先跑把 `lastGroup` 改写成 idle 变体 → B 查表恒落空 → 落回默认 idle 第 0 帧。

**实测 `touch_idle14` 出现两次回落**：3.08s → idle9（A 正确）→ 3.63s → idle（B 落错）。

### 它的修法

合并为单一 `_fallbackOnce()`：
1. 统一选组判据（`FALLBACK_FIX` > `chain.best` > `idleGroup`），不再按动作名分类
2. `_fbFor` 保证一个动作只回落一次，从结构上消除竞争
3. 回落内部 `startMotion` 不回写 `lastGroup`
4. `pose_keep` 命中才写，不命中不清空

### 我在它之前踩过的判据坑（已记录）

我用 `state.currentGroup` 判「回落是否正确」，看到 `idle2` 就以为成功。实测队列会**堵死**：

```
qLen=3（从不减少）
  队首  idle          started=true   ← 端 endT=-1，永不结束
  中间  touch_idle1   started=false  ← 从未启动
  队尾  idle2         started=false  ← 从未启动
参数 Param278/45/46 全程冻结（波动 0.000）
```

**组名变成 `idle2`，但画面仍由队首那个旧 `idle` 驱动。** 所以：
- 用户看画面说「停在默认 idle」——**对**
- 我看组名说「已经在 idle2」——**判据错了**

这个教训已写进 `PROJECT_STATUS.md`。
